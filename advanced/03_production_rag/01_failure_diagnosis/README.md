# 01 RAG 失败诊断

生产 RAG 的第一步不是调 prompt，而是判断失败发生在哪一层。

本章用一个固定案例演示：用户问“企业版支持 SSO 吗？”，系统答成“所有版本都支持 SSO”。我们先看 Top-K 和上下文，再决定修复方向。

## 为什么先做失败诊断

RAG 链路很长，同一个“答错了”可能来自完全不同的原因：

- 文档里本来就没有答案。
- 文档有答案，但切块后语义不完整。
- 正确 chunk 被召回了，但排在很后面。
- 正确 chunk 进入了上下文，但被无关 chunk 干扰。
- 模型没有遵守“只根据资料回答”的约束。
- 引用生成逻辑引用了错误来源。

如果不先分类，优化动作很容易走偏。例如 Top-K 里根本没有正确资料时，继续改 prompt 基本没有用；上下文里已经有正确证据但答案错时，优先改检索也不一定有效。

## 运行

```bash
uv run advanced/03_production_rag/01_failure_diagnosis/main.py
```

## 本章要点

- Top-K 里没有正确资料，叫“无召回”。
- Top-K 有正确资料但排得低，优先看排序、rerank、上下文截断。
- 上下文里有正确证据但答案错，才重点看 prompt、忠实度和引用约束。
- 生产排查要保存：用户问题、检索结果、上下文、答案、引用、模型配置。

## 排查时要保存什么

生产环境里，每次 RAG 请求至少应该能回放这些信息：

| 字段 | 作用 |
| --- | --- |
| `query` | 用户原始问题，排查是否问法模糊 |
| `rewritten_query` | 如果做了 query rewrite，要知道改写是否引入错误 |
| `filters` | 租户、权限、语言、版本等过滤条件 |
| `retrieved_chunks` | 第一阶段召回结果和分数 |
| `reranked_chunks` | rerank 后的排名和分数 |
| `packed_context` | 最终进入 LLM 的上下文 |
| `answer` | 模型最终回答 |
| `citations` | 回答引用了哪些来源 |
| `model_config` | 模型、温度、top_p、prompt 版本 |

没有这些记录，只看最终答案，很难判断该修哪一层。

## 判断顺序

```text
问题
  ↓
Top-K 是否包含正确 chunk？
  否 -> 召回问题
  是
  ↓
正确 chunk 是否靠前并进入上下文？
  否 -> 排序 / 截断问题
  是
  ↓
答案是否忠实使用上下文？
  否 -> 生成 / prompt / 引用问题
  是 -> 看答案完整性和用户意图
```

## 失败类型示例

| 失败类型 | 典型现象 | 例子 | 优先修复 |
| --- | --- | --- | --- |
| 无召回 | Top-K 里没有正确 chunk | 问 `E1024`，只召回了普通上传说明 | hybrid search、query rewrite、切块 |
| 排序低 | 正确 chunk 在 Top-K 后面 | 正确价格政策排第 9，最终只取前 3 | RRF、rerank、调大第一阶段 top_k |
| 上下文截断 | 正确 chunk 被召回但没进 prompt | Top-K 有答案，context limit 太小 | context packing、rerank 后截断 |
| 生成不忠实 | 上下文有正确证据但答案编造 | 文档说“企业版支持”，模型答“全部版本支持” | prompt、引用约束、faithfulness 检查 |
| 引用错误 | 答案对，但引用来源不支持结论 | 价格答案引用了登录 FAQ | citation precision 评估、引用绑定 |
| 权限错误 | 检索到其他租户或高权限文档 | 普通员工看到内部路线图 | metadata filter、租户隔离 |

## 如何读本章脚本输出

脚本会打印三段信息：

```text
Top-K 检索结果
```

先确认正确 chunk 是否出现。示例里 `pricing:enterprise` 出现在第 2 位，所以不是“无召回”。

```text
进入上下文的前 2 条
```

再确认正确 chunk 是否进入 LLM 上下文。示例里它进入了上下文。

```text
模型答案
```

最后对比答案和上下文。示例中上下文明确写了“个人版和团队版不包含 SSO”，但答案说“所有版本都支持 SSO”，所以属于“上下文有但回答错”。

## 修复策略选择

不同失败类型对应不同动作：

```text
无召回 -> 数据清洗 / 切块 / query rewrite / hybrid search
排序低 -> RRF / rerank / 调大召回 top_k
上下文有但回答错 -> prompt 约束 / 引用要求 / 忠实度评估
权限错误 -> metadata filter / 租户隔离
信息过期 -> active 标记 / updated_at / 版本化索引
```

经验规则：先修“看得到正确证据”，再修“排得足够靠前”，最后修“模型是否忠实使用证据”。

## 练习

2. 删除 `RETRIEVED` 中的 `pricing:enterprise`，观察诊断结果如何变成“无召回”。
3. 把 `MODEL_ANSWER` 改成“企业版支持 SSO，个人版和团队版不支持”，思考这时还需要修检索吗？
