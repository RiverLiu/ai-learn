# 02 Hybrid Search

向量检索擅长“语义相似”，关键词检索擅长“精确命中”。

错误码、参数名、套餐名、产品型号、人名、订单号这类词，往往不能只靠语义相似度。生产 RAG 通常会同时做向量检索和关键词检索。

## 为什么只用向量检索不够

向量检索会把文本变成 embedding，再按语义相似度找结果。它适合处理同义表达：

```text
用户：怎么退款？
文档：购买后 7 天内可以申请退费。
```

这两句话字面不完全一样，但语义接近，向量检索通常能找到。

但有些问题依赖精确 token：

```text
错误码 E1024 怎么处理？
S3UploadTimeout 参数是什么意思？
企业版 SSO 怎么开？
```

这些词一旦丢失，语义再接近也没用。用户问的是 `E1024`，不是泛泛的“上传失败”；问的是 `S3UploadTimeout`，不是任意超时参数。

## 运行

```bash
uv run advanced/03_production_rag/02_hybrid_search/main.py
```

## 本章要点

- 向量检索更容易找“意思相近”的内容。
- 关键词检索更容易命中 `E1024`、`S3UploadTimeout`、`SSO` 这类精确词。
- Hybrid Search 不是替代向量检索，而是多一路召回。
- 后续通常还需要 RRF 合并和 rerank 精排。

## 两类检索的差异

| 能力 | 向量检索 | 关键词检索 |
| --- | --- | --- |
| 同义表达 | 强 | 弱 |
| 错误码、参数名 | 不稳定 | 强 |
| 短查询 | 容易语义不足 | 命中词时很稳定 |
| 长自然语言问题 | 强 | 可能被无关词干扰 |
| 拼写错误 | 取决于模型 | 通常较弱 |
| 可解释性 | 需要看相似度和文本 | 容易解释命中了哪些词 |

生产系统里常见组合：

```text
vector_results = vector_search(query, top_k=20)
keyword_results = bm25_search(query, top_k=20)
merged = rrf(vector_results, keyword_results)
final = rerank(query, merged, top_n=5)
```

Hybrid Search 解决的是“多召回”，不是最终排序。合并和精排通常还要交给 RRF 和 rerank。

## 示例：语义问题

用户问：

```text
怎么退款
```

可能命中的文档：

```text
用户可以在购买后 7 天内申请退款，退款入口位于账单中心。
```

这个问题里“退款”本身就是关键词，同时也有明确语义，所以向量检索和关键词检索都容易命中。

## 示例：精确词问题

用户问：

```text
错误码 E1024 怎么处理
```

如果只靠语义，系统可能找出“上传失败”“网络超时”“文件限制”等相近内容，但不一定命中真正的 `E1024` 说明。

关键词检索会优先命中包含 `E1024` 的 chunk：

```text
错误码 E1024 表示上传文件超过大小限制，请压缩文件或升级套餐。
```

这就是 hybrid search 的价值：让语义召回和精确召回互补。

## 观察点

脚本会对两个问题分别打印：

- 简单语义检索结果
- 关键词检索结果

你会看到“怎么退款”这类问题语义检索表现不错；“错误码 E1024”这类问题关键词检索更稳定。

## 常见错误

- 只做向量检索，导致错误码、API 参数、型号找不到。
- 只做关键词检索，导致“退费”和“退款”这类同义表达召回不稳。
- 直接把两组结果拼接，导致重复 chunk 和排序混乱。
- 直接相加不同检索器的原始分数。向量相似度和 BM25 分数尺度不同，通常不能直接比较。
- 第一阶段 `top_k` 太小，导致后面的 RRF 和 rerank 没有足够候选。

## 练习

1. 在 `main.py` 里新增一个文档，包含 `SSO`，再查询“企业版 SSO 怎么开”。
2. 在 `DOMAIN_TERMS` 中删除 `E1024`，观察关键词检索结果变化。
3. 思考你的业务里有哪些必须精确命中的词：订单号、工单号、错误码、产品型号、法规条款编号，还是函数名？
