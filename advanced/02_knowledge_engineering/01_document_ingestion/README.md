# 01 文档摄取与知识库管道

RAG 的质量很大程度不取决于“最后怎么 prompt”，而取决于数据进入知识库之前是否被正确解析、清洗、切块、标注和更新。
本章讲生产知识库的数据管道。

## 本章要点

- 文档摄取是 RAG 的地基。
- 生产知识库必须处理文档格式、版本、权限、增量更新和删除。
- chunk 不是越小越好，也不是越大越好，要服务检索目标。
- 元数据设计决定后续能否做权限过滤、来源引用和问题定位。

## 数据管道全流程

```text
原始文件
  ↓
格式识别：PDF / DOCX / HTML / Markdown / CSV / 图片
  ↓
解析：文本、表格、标题、页码、图片说明
  ↓
清洗：去页眉页脚、去重复、修复乱码、统一空白
  ↓
结构化：章节、段落、表格、列表、代码块
  ↓
切块：按标题、段落、token、语义边界
  ↓
元数据：文档ID、版本、页码、权限、时间、来源URL
  ↓
embedding
  ↓
写入向量库和文档库
  ↓
增量更新、删除、重建
```

## 文档解析策略

| 格式 | 难点 | 建议 |
| --- | --- | --- |
| Markdown | 标题结构明显，但链接和代码块要保留 | 优先按标题切块 |
| HTML | 导航、广告、脚本噪声多 | 先提正文，再保留 URL 和标题 |
| PDF | 页眉页脚、分栏、扫描件、表格复杂 | 区分文本 PDF 和扫描 PDF |
| DOCX | 样式、表格、批注、修订痕迹 | 保留标题层级和表格结构 |
| CSV/Excel | 行列结构强，不适合直接当普通文本 | 转成记录摘要或表格检索 |
| 图片 | 需要 OCR 或视觉模型 | 保存图片来源和识别置信度 |

## 清洗规则

清洗不是把文本变“漂亮”，而是提高检索和引用质量。

常见清洗：

- 删除重复页眉页脚。
- 合并被 PDF 换行打断的句子。
- 保留标题层级。
- 统一全角/半角和空白。
- 删除无意义导航文本。
- 标记表格标题和列名。
- 保存原始页码和来源。

不要过度清洗：

- 不要删除法律、价格、限制条件等看似重复但实际重要的条款。
- 不要把表格直接压成一串无结构文本。
- 不要丢失页码、URL、文件名和更新时间。

## 元数据设计

推荐每个 chunk 至少包含：

```json
{
  "chunk_id": "doc_001:v3:chunk_018",
  "document_id": "doc_001",
  "document_version": 3,
  "source_type": "pdf",
  "source_uri": "s3://kb/product_manual.pdf",
  "title": "产品手册",
  "section": "计费规则",
  "page_start": 12,
  "page_end": 13,
  "tenant_id": "acme",
  "permission_group": "support",
  "created_at": "2026-08-08T10:00:00+08:00",
  "updated_at": "2026-08-08T10:00:00+08:00"
}
```

这些字段服务于：

- 权限过滤
- 引用展示
- 文档版本回滚
- 评估失败定位
- 增量更新和删除

## 切块策略

### 固定窗口

优点：实现简单，适合入门。

缺点：容易切断语义，引用不自然。

适合：

- 普通长文本
- 结构不明显的文档
- 原型阶段

### 结构感知

按标题、段落、列表、表格切块。

优点：保留语义边界。

缺点：实现复杂，需要解析器质量稳定。

适合：

- 产品文档
- 帮助手册
- 规章制度
- API 文档

### 父子 chunk

小 chunk 用于检索，大 chunk 用于生成。

```text
检索：段落级 chunk
生成：返回所属章节或相邻上下文
```

适合答案依赖上下文的场景，例如合同、政策、技术文档。

## 增量索引

生产知识库不能每次全量重建。需要设计：

- 文档指纹：hash 文件内容或正文。
- 版本号：每次更新产生新版本。
- 删除策略：删除旧 chunk 或标记失效。
- 重建策略：解析规则变化时批量重建。
- 幂等写入：重复跑任务不会产生重复 chunk。

推荐状态机：

```text
uploaded → parsing → parsed → chunking → embedding → indexed → active
                                  ↓
                               failed
```

## 常见坑

- 只存向量，不存原文和元数据，后期无法引用和排查。
- 文档更新后旧 chunk 还在，模型回答过期信息。
- 多租户知识库没有权限过滤，造成数据泄露。
- PDF 解析结果顺序错乱，检索命中但答案不可用。
- 表格被切碎，价格、套餐、限制条件丢失。

## 具体示例：把一篇 FAQ 文档变成可索引 chunk

原始 Markdown：

```markdown
# 云雀笔记 FAQ

## 会员可以退款吗？

购买后 7 天内可以申请退款。超过 7 天后，已支付费用不退还。

## 数据会保留多久？

会员到期后，数据至少保留 90 天。
```

结构化解析后：

```json
[
  {
    "section": "会员可以退款吗？",
    "text": "购买后 7 天内可以申请退款。超过 7 天后，已支付费用不退还。"
  },
  {
    "section": "数据会保留多久？",
    "text": "会员到期后，数据至少保留 90 天。"
  }
]
```

写入索引前的 chunk：

```json
{
  "chunk_id": "faq:v1:0001",
  "document_id": "faq",
  "document_version": 1,
  "title": "云雀笔记 FAQ",
  "section": "会员可以退款吗？",
  "text": "购买后 7 天内可以申请退款。超过 7 天后，已支付费用不退还。",
  "metadata": {
    "tenant_id": "public",
    "source_uri": "data/knowledge_base/faq.md",
    "source_type": "markdown",
    "chunk_index": 1,
    "document_status": "active"
  }
}
```

用户问“买错会员能退吗？”时，系统不只把 text 送给模型，还能把 `source_uri` 和 `section` 显示给用户：

```text
答案依据：云雀笔记 FAQ / 会员可以退款吗？
```

这就是为什么数据管道必须保留元数据。没有元数据，模型即使答对，也无法解释答案来自哪里。

## 实践任务

为 [tutorials/rag/knowledge_base](../../../tutorials/rag/knowledge_base/) 设计一个生产版摄取管道：

1. 为每个 Markdown 文件生成 `document_id` 和版本号。
2. 按标题切块。
3. 为每个 chunk 添加 `source_uri`、`section`、`chunk_index`。
4. 支持文件内容未变化时跳过 embedding。
5. 输出一份 `manifest.json`，记录每个文档的状态。
