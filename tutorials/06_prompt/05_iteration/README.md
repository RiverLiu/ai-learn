# 05 提示词迭代：用数据而不是感觉调提示词

"我觉得这版提示词读起来更专业"不算数。工程上迭代提示词的正确姿势是：
**造一个评估集 → 每版提示词跑一遍 → 自动打分 → 看得分表决定哪版上线。**
从此改提示词从玄学变成可度量的工程活动。

## 本章要点

- **评估集**：5 条有代表性的客服问题 + 人工给定的标准答案关键词
  （如"专业版多少钱一个月？" → 答案里必须出现"18元"）。
  其中故意放了一条资料里没有的问题（"学生优惠"），考察模型会不会老实说"不清楚"。
- **两版提示词**：v1 只给了角色（"你是客服助手"），v2 补齐四要素
  （事实资料 + "没有就说不知道"的约束 + 格式要求）。
- **自动打分**：程序逐条调用、统计关键词命中率，打印两版得分表——
  v1 因为手里没有事实资料只能编造，命中率暴露一切。
- **定性 + 定量**：得分表之外，再抽一条最能说明问题的回答做定性对比。

## 运行

```bash
uv run tutorials/06_prompt/05_iteration/main.py
```

注意：本章会对评估集逐条真实调用 API（5 条 × 2 版 = 10 次调用），耗时稍长。

## 核心概念

- **评估集（eval set）**：一小批"输入 + 标准答案"，是提示词工程的"单元测试"。
  评估集不需要大，但要覆盖典型情况和容易出错的边界情况。
- **关键词命中率**：本章用最简单的自动评分——答案里是否出现标准答案的关键词。
  它粗糙但够用；更精细的做法是用另一个 LLM 当裁判打分，这是 evaluation 模块的内容。
- **迭代循环**：写提示词 → 跑评估 → 看哪条错了 → 针对性改提示词 → 再跑评估。
  每次只改一处，才知道是哪处起了作用——和调 bug 一个道理。

## 常见错误

1. **凭感觉改提示词**："这版看起来更好"——不跑评估集，永远不知道是不是真的更好，
   更不知道改动是否把原来对的弄错了（回归）。
2. **评估集没有"陷阱题"**：评估集全是简单题，两版提示词得分一样，看不出差异。
   一定要放边界情况（本章的"学生优惠"）。
3. **一次改好几处**：约束、格式、示例全改了，得分涨了却不知道是哪处的功劳。

## 练习建议

1. 给评估集加第 6 条："免费版的单个附件最大是多少？"（关键词：`100MB`），
   运行观察两版得分变化。
2. 把 v2 里"一律回答'抱歉，这个我还不清楚'"删掉再跑评估，
   观察"学生优惠"那条的得分如何变化（体会每条约束对得分的贡献）。
3. 写一版 v3 提示词（比如在 v2 基础上要求"分点列出"），跑评估对比 v2 与 v3，
   决定哪版"上线"。
