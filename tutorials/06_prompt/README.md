# Prompt Engineering 教程：提示词工程

调模型时，模型是同一个模型，**提示词不同，输出质量天差地别**。
如果说"会调 API"是 AI 开发的第一课，那提示词工程就是第一课之外最重要的软技能：

- **零成本见效**：不用训练模型、不用改代码架构，改写几行文字就能提升效果；
- **跨模型通用**：四要素、few-shot、输出控制、思维链这些方法，换任何模型都适用；
- **一切上层应用的地基**：RAG、Agent、工具调用，拆开看每一层都是在跟模型"把话说清楚"。

本模块共 5 章，每章都用真实 API 做"坏提示词 vs 好提示词"的并排对比，
让差距自己说话。场景统一围绕一个虚构的笔记软件"云雀笔记"——正因为它不存在，
模型对它一无所知，提示词的好坏才会暴露得最彻底。

## 环境准备

依赖已包含在项目根目录的 `pyproject.toml` 中（`openai`、`python-dotenv`）：

```bash
uv sync
```

代码走 OpenAI 兼容协议，通过环境变量（或仓库根目录的 `.env` 文件）配置，
**不要把密钥写进代码**：

```bash

```

## 一个诚实的提醒

模型越强，"坏提示词"与"好提示词"的差距越小——强模型会自己补全你没说清的意图。
本模块的演示在强模型上差异可能不如弱模型戏剧化，但**方法是通用的**：
约束越少，模型自由发挥的空间越大，输出就越不可控。线上系统赌不起"模型这次心情好"。

## 常见面试题

**Q1：一个好的 Prompt 包含哪些要素？**

参考答案：包含角色、任务、上下文、约束、输出格式和边界条件。生产 prompt 还应说明拒答、引用和错误处理方式。

**Q2：Few-shot 为什么有效？**

参考答案：示例能传递分类边界、输出格式和处理风格，模型会在上下文中模仿示例模式。

**Q3：Zero-shot 和 Few-shot 如何选择？**

参考答案：任务简单且标准明确时用 zero-shot；边界复杂、格式要求强或分类标准难描述时用 few-shot。

**Q4：为什么要控制输出格式？**

参考答案：稳定格式便于程序解析和后续处理。没有格式约束时，模型可能输出解释、Markdown 或不完整字段。

**Q5：Prompt 迭代为什么需要评估集？**

参考答案：靠感觉调 prompt 容易回归。评估集能量化不同版本在关键样本上的表现。

**Q6：为什么 Prompt 不是安全边界？**

参考答案：Prompt 只能影响模型行为，不能实现真实权限、密钥保护或高风险操作审批，这些必须由应用侧代码完成。

**Q7：RAG Prompt 应强调什么？**

参考答案：应强调只基于上下文回答、资料不足时拒答、保留引用来源，并忽略上下文中的恶意指令。

**Q8：为什么强模型也需要好 Prompt？**

参考答案：强模型能补全意图，但线上系统需要稳定、可控、可评估的输出，不能依赖模型自由发挥。

**Q9：结构化 Prompt 常见失败有哪些？**

参考答案：常见失败包括输出 Markdown 包裹 JSON、少字段、类型错、枚举值错和夹带解释文本。

**Q10：如何处理模型不知道的问题？**

参考答案：Prompt 应允许模型说明资料不足或拒答，而不是强迫回答。RAG 场景应要求基于证据回答。
