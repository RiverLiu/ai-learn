# 02 zero-shot vs few-shot：用示例传递分类标准

不给示例直接让模型干活，叫 **zero-shot**；在提示词里放几个"问题 → 标准答案"的示例再提问，
叫 **few-shot**。few-shot 的价值不是"教模型学会新知识"，而是把**你这套业务里不成文的规则**
（分类边界、格式偏好、语气风格）用示例传递给它——这是语言描述很难写全的东西。

## 本章要点

- **任务**：把用户留言分类为 咨询 / 投诉 / 夸赞 / 闲聊，其中埋了两条"内部规定"：
  涉及退款/取消订阅一律算投诉；既有提问又有不满以投诉为准。
- **现场对比**：zero-shot 只给四个类别名，踩在规定上的边界留言（如 T1"取消订阅"，
  语气平静地"问入口"）会被按字面分成咨询；few-shot 加 3 个带标注的示例后全部命中——
  示例里隐含了那两条规定。
- **关键认识**：zero-shot 分错不代表模型能力不行，而是它**不可能猜到**你的内部规定；
  few-shot 是传递这类"潜规则"最省事的办法。
- **选示例的原则**：贵精不贵多——挑能代表边界规则的示例，比堆几十个普通示例有效。

## 运行

```bash
uv run tutorials/06_prompt/02_fewshot/main.py
```

## 核心概念

- **zero-shot / few-shot**：区别在于提示词里有没有"输入 → 输出"的示例对。
  示例本身就是最精确的规则说明书。
- **示例即规则**：模型会从示例中归纳出模式，包括你没有明说的模式。
  所以示例必须覆盖"容易分错的边界"，而不只是"最典型的正常情况"。
- **思考型模型的 token 预算**：本章分类只需输出一个词，但 `max_tokens` 仍要给足
  （思考型模型会先消耗推理 token，预算太小会返回空串）——这是调 API 时的实战经验。

## 常见错误

1. **示例与规则矛盾**：示例标注错了（比如把退款咨询标成"咨询"），模型会照错的学。
   写 few-shot 示例前先确保标注本身符合你的业务规定。
2. **示例全是"简单题"**：示例全是典型情况，模型依然不知道边界怎么处理。
   示例的边际价值在于覆盖边界。
3. **以为示例越多越好**：示例堆太多，既费 token 又可能引入相互矛盾的模式；
   一般 2~5 个精心挑选的示例足够，不够再迭代（见第 5 章）。

## 练习建议

1. 把示例 2 的标注从"投诉"改成"咨询"，重新运行，观察 T1 的分类结果如何被带偏。
2. 新增一条测试留言："你们的价格页面做得真清楚，一看就懂"（标准答案：夸赞），
   看 zero-shot 与 few-shot 是否都能答对。
3. 尝试把 3 个示例压缩成 2 个（去掉示例 3），运行观察 T2 是否仍然正确，
   体会"示例覆盖边界"的含义。
