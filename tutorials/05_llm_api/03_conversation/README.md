# 03 多轮对话：模型没有记忆

ChatGPT 里模型能记住你十分钟前说的话，但 API 不会——每次请求都是全新的。
本章先演示"失忆"，再演示"带历史就记得"，最后写出一个 5 轮对话循环。

## 本章要点

- **API 是无状态的**：两次独立调用互不知晓，服务器不保存上下文。
- **"记忆"是客户端维护的**：把历史消息（含模型自己的 `assistant` 回答）原样
  追加进 `messages`，每次全量重发——模型读到的列表长了，回答自然连贯。
- **对话循环骨架**：`append(user)` → 调用 → `append(assistant)` → 循环。
  本章用预置问题列表模拟用户输入，真实产品换成 `input()` 即可。

## 运行

需要先配好 `.env`（见[模块首页](../README.md#环境准备)），然后在仓库根目录：

```bash
uv run tutorials/05_llm_api/03_conversation/main.py
```

预期：第 1 节模型答不出你的名字；第 2 节答得出；第 3 节 5 轮里"这道菜""不辣的版本"
等指代都能被正确理解。

## 核心概念

- **上下文（context）**：发给模型的完整消息列表。它既是模型的"记忆"，也是计费来源——
  每轮都把全部历史重发，轮数越多 token 越贵。
- **上下文窗口有上限**：每个模型有最大 token 数（如 128K）。聊太久会超限报错，
  工程上的对策是截断、摘要或检索式记忆（memory 模块专门讲）。
- **assistant 消息不能省**：只发用户消息不发模型回答，模型就不知道自己说过什么，
  对话会"精神分裂"。

## 常见错误

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 模型永远不记得上一轮 | 每轮都新建了空列表 | 在循环外创建 `messages`，循环内 append |
| 对话前后矛盾 | 只 append 了 user，没 append assistant | 两者都要追加 |
| 聊久了报"context length exceeded" | 历史超过模型上下文窗口 | 截断早期消息 / 摘要压缩（第 5 章也会提到） |
| 越聊越贵、越聊越慢 | 正常现象：历史全量重发 | 同上，控制上下文长度 |

## 练习建议

1. 把 `QUESTIONS` 换成你自己的 5 轮追问（如"推荐一本书 → 作者是谁 → 还写过什么"），
   观察指代是否依然正确。
2. 在第 3 节循环里打印每轮的 `response.usage.prompt_tokens`，画出输入 token 随轮数
   增长的曲线，理解"越聊越贵"。
3. 给循环加一条规则：只保留最近 4 条消息（system 除外），观察第 5 轮时模型是否
   忘掉第 1 轮的内容——这就是"滑动窗口"记忆策略。
