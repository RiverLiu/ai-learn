# 05 错误处理、重试与成本估算

Demo 一次成功不代表代码能上线。真实的网络世界里，限速、超时、断线是日常。
本章给调用加上"韧性"：认清错误类型、实现指数退避重试、会用 usage 算成本。

## 本章要点

- **常见错误对照表**（均为 `openai.APIStatusError` 的子类或相关异常）：

  | 错误 | 异常类型 | 含义 | 对策 |
  | --- | --- | --- | --- |
  | 401 | `AuthenticationError` | 密钥错误/失效 | 检查 `.env`，重试无用 |
  | 404 | `NotFoundError` | 模型名错 / base_url 多拼了路径 | 检查 `MODEL_NAME`、`OPENAI_BASE_URL` |
  | 429 | `RateLimitError` | 请求太频繁 / 额度不足 | **退避重试** |
  | 超时 | `APITimeoutError` | 网络慢或服务繁忙 | **退避重试**，调大 `timeout` |
  | 5xx | `InternalServerError` | 服务端故障 | **退避重试** |
  | 上下文超长 | `BadRequestError`（400） | 消息总长度超模型窗口 | 截断/压缩历史（第 3 章） |

- **指数退避重试**：只重试"过会儿可能自己好"的错误（429/超时/断线/5xx），
  等待 1s → 2s → 4s 逐次翻倍，超过上限放弃；配置类错误（401/404/400）立即抛出。
- **成本估算**：`成本 = 输入 token × 输入单价 + 输出 token × 输出单价`，
  数据全在 `response.usage` 里；思考型模型的推理 token 也按输出计费。

## 运行

需要先配好 `.env`（见[模块首页](../README.md#环境准备)），然后在仓库根目录：

```bash
uv run tutorials/05_llm_api/05_errors_retry/main.py
```

说明：重试演示用"模拟错误"方式——把超时设为 0.001 秒必然触发 `APITimeoutError`，
能看到 1s → 2s 的退避节奏后放弃；404 则不重试立即抛出。不会去真触发 429。

## 核心概念

- **为什么"退避"**：限速/故障时立刻重试只会加重服务端压力，指数级拉长间隔
  既给对方喘息时间，也提高自己下一次成功的概率。生产里还会加随机抖动（jitter）
  防止大量客户端"同拍重试"。
- **SDK 自带重试**：OpenAI SDK 默认自带 2 次重试（`OpenAI(max_retries=0)` 可关闭）。
  本章为看清机制自己实现；真实项目用 SDK 自带或 tenacity 等库均可，原理相同。
- **幂等性**：chat 接口本质是"读"操作，重试安全；涉及扣费/下单的"写"接口重试前
  必须确认幂等，否则可能重复执行。

## 常见错误

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 所有错误都被重试 | except 捕获面太宽 | 只捕获可重试类型，其余放行 |
| 重试后更糟（触发更重限速） | 固定间隔 / 间隔太短 | 指数退避 + 随机抖动 |
| 永远重试不退出 | 没有次数上限 | `max_attempts` 兜底，耗尽后抛出 |
| 以为没花钱 | 没看 `usage` | 每次调用记录 token 数，定期汇总 |

## 练习建议

1. 给 `chat_with_retry` 加随机抖动：`delay *= random.uniform(0.5, 1.5)`，想想为什么
   这能防止"惊群"。
2. 把 429 也纳入演示：本地写一个假 client（前两次调用抛 `RateLimitError`、第三次
   返回正常对象），验证重试封装能"熬到成功"。
3. 修改成本演示：连续调用 3 次并累计 `total_tokens`，估算"每天 1 万次这样的调用"
   的月成本。
