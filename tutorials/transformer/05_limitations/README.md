# 05 Transformer 的限制与工程启发

理解 Transformer 的限制，能帮助你更好地设计 Prompt、RAG、Agent、评估和生产系统。

## 本章要点

- Transformer 不是数据库，它是概率生成模型。
- 上下文窗口有限，且长上下文成本高。
- 模型可能幻觉、遗漏、受干扰或过度自信。
- 工程上要用 RAG、工具、评估和观测来补足模型限制。

## 限制 1：上下文窗口有限

模型每次请求只能处理一定数量的 token。

```text
系统提示词 + 用户问题 + 历史消息 + RAG 上下文 + 工具结果 + 输出
```

这些都要占用上下文窗口。

工程启发：

- 多轮对话要做历史裁剪或摘要。
- RAG 要检索相关内容，而不是塞入所有文档。
- 工具结果要摘要后再放回上下文。

## 限制 2：长上下文成本高

Self-Attention 需要计算 token 之间的关系。上下文越长：

- 计算越贵
- 延迟越高
- 更容易混入干扰信息
- RAG 引用更难控制

工程启发：

- 控制 top_k。
- 使用 rerank。
- 去重和压缩上下文。
- 记录每次请求 token 成本。

## 限制 3：幻觉

模型会生成看似合理但不一定真实的内容。

原因包括：

- 训练目标是预测 token，不是验证事实。
- 上下文缺少必要证据。
- Prompt 诱导模型猜测。
- 检索内容错误或过期。

工程启发：

- RAG 回答要求引用来源。
- 不知道时允许拒答。
- 对关键任务使用工具查询真实系统。
- 用评估集检查 forbidden facts。

## 限制 4：位置和表述敏感

Prompt 顺序、格式、示例和上下文噪声都会影响输出。

工程启发：

- Prompt 要版本化。
- 对关键任务写回归测试。
- Few-shot 示例要覆盖边界情况。
- 重要约束放在清晰位置，不要埋在长文本中。

## 限制 5：不能可靠执行外部动作

模型本身只能生成 token。发邮件、查数据库、退款、写文件都必须通过外部工具执行。

工程启发：

- 工具调用要做参数校验。
- 高风险操作要人工确认。
- 工具执行结果要写回上下文。
- 记录工具调用轨迹。

## 一张工程对照表

| Transformer 限制 | 工程解决方案 |
| --- | --- |
| 上下文有限 | 记忆裁剪、摘要、RAG |
| 不知道最新事实 | 工具查询、RAG、联网检索 |
| 会幻觉 | 引用、拒答、评估、事实校验 |
| 输出不稳定 | 结构化输出、低 temperature、回归测试 |
| 长上下文贵 | rerank、压缩、缓存、成本监控 |
| 不能执行动作 | tool calling、MCP、人工审批 |
