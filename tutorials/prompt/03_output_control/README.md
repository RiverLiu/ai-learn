# 03 强制 JSON 输出：让程序能解析模型的回答

模型天生说的是"人话"，而程序需要的是结构化数据。让模型输出**可解析的 JSON**，
是把 LLM 接进任何系统的第一步——但"用 JSON 返回"这五个字远远不够：
模型很可能裹一层 ```` ```json ```` 围栏、再附赠两句解释，`json.loads` 当场报错。

## 本章要点

- **现场对比**：只说"用 JSON 返回" → 输出带 markdown 围栏，`json.loads` 抛
  `JSONDecodeError`；改进提示词（明确 schema、"只输出 JSON 本身、不要围栏、不要解释"）
  → 一次解析成功。
- **可解析提示词的三件套**：
  1. 写明 **schema**（字段名、类型、取值范围），不给模型自由发挥的余地；
  2. 明说"**只输出 JSON 本身**"，禁止围栏和解释；
  3. 把模型定位成"信息抽取**程序**"而不是"助手"（角色影响输出风格）。
- **工程兜底**：提示词再严格也要 `try/except`——解析失败时把错误反馈给模型
  **重问一次**（多轮对话的典型用法），两次都失败再降级（人工 / 默认值）。

## 运行

```bash
uv run tutorials/prompt/03_output_control/main.py
```

## 核心概念

- **模型输出是概率不是保证**：同一条提示词，绝大多数时候输出合法 JSON，
  也总会偶尔失手。工程上要把"解析失败"当作正常分支处理，而不是异常事故。
- **重问（retry with feedback）**：把模型的原输出和解析报错一起喂回去让它修正，
  比简单重试成功率高——模型知道自己错在哪。
- **更进一步的工具**：生产环境还可以用 JSON Schema 校验字段、用厂商提供的
  structured output / response_format 能力从协议层强制 JSON（见
  [langchain 教程第 2 章](../../langchain/02_prompts_parsers/)的输出解析器）。
  本章先用纯提示词把原理讲透。

## 常见错误

1. **只说"用 JSON"不说 schema**：模型自己起字段名（`"星级"`、`"score"`、`"rate"`），
   每次都不一样，下游根本没法取字段。
2. **解析失败就崩溃或不管**：把 `json.loads` 裸写在主流程里，一次围栏输出就让程序挂掉。
3. **重试时不带上下文**：失败后原样重发同样的请求，模型可能再犯同样的错；
   正确做法是带上原输出和报错信息重问。

## 练习建议

1. 在 schema 里增加一个 `summary` 字段（一句话总结评论，不超过 20 字），
   修改好提示词并运行，确认解析后的字段齐全。
2. 把 `extract_with_retry` 的重问次数从 1 次改成 2 次，并给每次重问的提示词
   加上第几次的编号，观察输出。
3. 写一个新的抽取任务（如：从一段招聘文案中抽取 `position`、`salary`、`skills`），
   先故意用坏提示词观察失败，再写出能让 `json.loads` 一次成功的好提示词。
