# 04 质量检查清单

本章用于在 Skill 上线前做最后检查，也适合后续迭代时复盘。

## 一句话标准

一个好 Skill 应该让 Agent 在面对同类任务时：

- 更容易判断该不该接手。
- 更快找到相关资料。
- 更少重复写脆弱代码。
- 更稳定地产出符合团队标准的结果。

## 上线前检查

### 触发是否清楚

检查 `description`：

- 是否说明了 Skill 能做什么？
- 是否写了具体触发场景？
- 是否包含用户可能使用的同义词？
- 是否过宽，导致大量无关任务也会触发？
- 是否过窄，导致真实任务匹配不到？

建议用 5 个“应该触发”和 5 个“不该触发”的请求做人工测试。

### 正文是否可执行

检查 `SKILL.md` 正文：

- 是否有明确步骤？
- 是否说明先做什么、后做什么？
- 是否说明失败时怎么办？
- 是否说明输出格式？
- 是否说明哪些资料需要按需读取？
- 是否避免了大段泛泛背景？

正文应该像工作流，不应该像百科词条。

### 资源拆分是否合理

检查资源目录：

- `references/` 是否按场景命名？
- `scripts/` 是否只放真正需要确定性执行的脚本？
- `assets/` 是否只放会被输出或复制使用的模板/静态文件？
- `SKILL.md` 是否清楚导航到这些资源？

如果 Agent 不知道何时读取某个资源，这个资源就等于不可用。

### 脚本是否可靠

检查脚本：

- 是否有清晰参数？
- 是否能在缺少输入时给出友好错误？
- 是否避免默认覆盖用户文件？
- 是否已用代表性样例运行过？
- 是否输出机器和人都容易读的结果？

脚本越接近生产数据，越要保守处理文件写入和外部系统调用。

### 输出是否稳定

检查产物：

- 是否定义结构？
- 是否有字段名、表格列或模板？
- 是否说明引用资料的方式？
- 是否要求列出不确定性和缺失信息？

对于报告、审查、迁移、部署类 Skill，输出结构尤其重要。

## 常见问题

### Skill 写成了大 prompt

症状：`SKILL.md` 很长，所有细节都在正文里。

处理：保留核心流程，把详细规则拆到 `references/`。

### Skill 写成了工具列表

症状：只列出能用哪些工具，没有告诉 Agent 什么时候用、怎么组合、失败怎么处理。

处理：补充工作流和决策条件。工具清单不是 Skill，工具使用方法才是 Skill 的价值。

### Skill 太抽象

症状：写了“保持专业、注意质量、认真检查”等空泛要求。

处理：换成可观察规则，例如“报告必须包含 Executive Summary、Metric Table、Risks、Next Actions”。

### Skill 过度脚本化

症状：开放式判断也被强行写成脚本，导致 Agent 无法根据上下文调整。

处理：把脚本用于确定性任务，把判断逻辑留给文本流程和示例。

### 资源没人会读

症状：`references/` 里有很多文件，但 `SKILL.md` 没有提到。

处理：在正文加入资源导航：

```markdown
For authentication risks, read `references/auth.md`.
For database migration review, read `references/database.md`.
```

## 迭代方法

Skill 的迭代来自真实失败：

1. 记录一次失败任务。
2. 判断失败属于触发错误、流程缺失、资料缺失、脚本缺失还是输出约束缺失。
3. 修改最小必要位置。
4. 用相似但不同的请求再测试一次。

不要因为一次失败就把所有细节塞进 `SKILL.md`。先判断信息应该属于哪一层。

## 评估样例

可以为每个 Skill 保存一组评估请求：

```text
should_trigger:
  - 帮我检查这个 FastAPI PR 有没有鉴权漏洞
  - Review these route handlers and missing tests
  - 这个 Depends 写法为什么让 /docs 多了 args kwargs

should_not_trigger:
  - 解释一下 HTTP 状态码
  - 写一个普通 Python 排序函数
  - 介绍 FastAPI 是什么
```

每次改 `description` 后重新跑一遍这些样例，防止触发范围漂移。

## 最终检查清单

- `SKILL.md` 存在。
- frontmatter 只有必要字段，至少包含 `name` 和 `description`。
- `name` 简短、稳定、面向任务。
- `description` 覆盖能力和触发场景。
- 正文包含可执行工作流。
- 长资料已拆到 `references/`。
- 重复、脆弱、确定性步骤已脚本化。
- 模板和静态素材放在 `assets/`。
- 正文说明何时读取每个关键资源。
- 脚本已运行代表性测试。
- 输出格式和验收标准清楚。
