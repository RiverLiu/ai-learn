# 01 流水线模式：调研 → 写作 → 审校

多 Agent 不一定复杂。步骤固定、无分支无回路的任务，最顺手的形态是**流水线**：
把任务拆给几个职责单一的"专家"节点排成一条直线，产出沿 State 单向流动——
调研提炼卖点、写手负责成文、审校核对定稿。

## 本章要点

- 流水线 = 若干专家节点 + 固定顺序的边：State 单向流动，没有条件边，更没有循环。
- 每个节点是一次独立的 LLM 调用，提示词各自为政：职责单一，才能独立替换、独立测试。
- 节点之间靠 State 字段交接（`points` / `draft` / `final`）——交接物定义清楚，链路才可维护。
- 每个节点甚至可以配不同模型（写作用好模型、审校用便宜模型）；本章从简，共用一个。

## 运行

```bash
uv run tutorials/19_multi_agent/01_pipeline/main.py
```

预期输出：【调研】3 条卖点 →【初稿】一段文案 →【定稿】审校后的版本。

## 核心概念

- **与 LCEL 链的区别**：链上每一步只拿到上一步的输出；图的节点共享整个 State——
  本章审校节点同时读得到"资料"与"初稿"，才能做事实核对。
- **什么时候该拆节点**：一个提示词里出现"先 A、再 B、最后 C"时，
  就是该拆成流水线的信号。拆开之后每一步的提示词都变短，质量反而更稳。
- **流水线的边界**：步骤必须固定。一旦"根据中间结果决定去向"
  （比如审校不达标要打回重写），就需要条件边——那是下一章的内容。

## 常见错误

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 一个节点提示词又臭又长 | 该拆的步骤没拆 | 按职责拆节点，各自一句话人设 |
| 下游节点开始跑题 | 把上游所有产出无脑塞给下游 | 只传它需要的 State 字段 |
| 想让流程"看情况分叉" | 任务本就不适合流水线 | 改用条件边，见第 2 章 |

## 练习建议

1. 在写作前加一个"起标题"节点，让最终交付包含标题与正文。
2. 给审校加一条条件边：不达标就打回写手重写（流水线变成循环，对照
   [langgraph 02 章](../../10_langgraph/02_conditional/)）。
3. 给写手节点单独换一个更强的模型，对比产出差异。
