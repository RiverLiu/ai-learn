# 02 主管模式：一个中枢决定派给谁

流水线的步骤是写死的；当每轮都要看情况决定"这事该谁办"时，把判断集中到一个
**supervisor（主管）节点**：它自己不干活，只分派。worker 节点各管一摊，被点到名的那个
负责回答。这就是主管模式——客服分诊、任务调度都是它。

## 本章要点

- 结构 = supervisor 节点 + 条件边 + 若干 worker：supervisor 用**结构化输出**给出
  分派决定，路由函数把决定翻译成节点名——就是
  [langgraph 02 章](../../10_langgraph/02_conditional/)的条件边，只是路由依据换成了 LLM 判断。
- **决策与机制分离**：LLM 只负责"选谁"，图负责"怎么去"。改路由规则不用动提示词，
  换提示词不用动图。
- 本章 worker 答完回 `END`（一次性问答）；若需要 worker 汇报、主管再决定下一步，
  把边指回 supervisor 即成循环——结构不变，只改一条边。
- **与 [deepagents 03 章](../../14_deepagents/03_subagents/)的关系**：`task` 工具就是框架
  托管版的"主管分派"。那里子代理上下文隔离、跑完整 Agent 循环，成本与隔离性都更高；
  本章的 worker 是共享 State 的单次调用节点——同一原理，两种重量级。

## 运行

```bash
uv run tutorials/19_multi_agent/02_supervisor/main.py
```

预期输出：三个问题分别被 `[主管]` 分派给查价员、退款员、闲聊员，并由对应 worker 回答。

## 核心概念

- **结构化输出做路由**：`Literal["price", "refund", "chat"]` 限定取值，
  分派结果可解析、可校验——不会出现"模型说了一段话但程序不知道该怎么走"。
- **类别描述就是主管的员工手册**：每个类别的判定标准写不清楚，分派就会漂移。
  生产系统里通常会再给每个类别配一两条示例（few-shot）。

## 常见错误

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| supervisor 自己开始答题 | 提示词没说"只分派不回答" | 明确职责，回答留给 worker |
| 图报错"找不到节点" | 路由函数返回值与 `add_node` 的名字对不上 | 用一张映射表集中管理（本章的 `route`） |
| 同类问题忽而派这忽而派那 | 类别判定标准模糊 | 给每个类别一句判定标准，必要时加示例 |

## 练习建议

1. 加第 4 个 worker（如"技术支持"），只改提示词和映射表，观察主管是否自动学会新类别。
2. 把 worker 的边从 `END` 改回 `supervisor`，实现"分派 → 汇报 → 再分派"的循环。
3. 故意把某个类别的描述写模糊，运行几次观察误分派，体会"员工手册"的重要性。
