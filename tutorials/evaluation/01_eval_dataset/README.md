# 01 评估集构建：先有问题，才有评估

改了提示词、换了模型之后，"效果有没有变好"？没有一份固定的评估集，这个问题
只能靠"跑两条看看感觉"。本章围绕"云雀笔记"知识库手工构建一份 10 条的 QA 评估集，
让 LLM 逐条作答，再用最朴素的关键词命中率打分——并亲眼看看这个指标为什么不靠谱。

## 本章要点

- **评估集三要素**：`question`（用户怎么问）、`expected_answer`（参考答案）、
  `source`（答案依据的文档，第 2、3 章会用到它）。`keywords` 是从参考答案里
  人工挑出的关键事实，仅供本章的朴素指标使用。
- **jsonl 格式**：一行一条 JSON，方便追加、做 diff、流式读取，是评估集的常见存法。
- 代码流程：加载评估集 → LLM 逐条生成回答（**缓存到 `answers_cache.json`**，
  重复运行不再调用 API）→ 统计关键词命中率。
- **关键词匹配的两大失灵**：答错了但关键词全中（假阳性）、答对了换个说法就全不中
  （假阴性）——脚本末尾用两个构造好的反例把这两点钉死，引出下一章的 LLM-as-judge。

## 运行

需要聊天模型密钥（`OPENAI_API_KEY`，第三方服务追加 `OPENAI_BASE_URL` / `MODEL_NAME`）：

```bash
uv run tutorials/evaluation/01_eval_dataset/main.py
```

预期输出：10 条问题逐条打印生成回答与逐关键词命中情况（`✓`/`✗`）、整体命中率，
最后是两个反例演示。首次运行要调用 10 次 LLM，之后命中缓存秒出。

## 核心概念

- **评估集就是回归测试**：提示词、模型、参数任何改动之后重跑一遍，分数可比、退化可查。
- **评估集从哪来**：真实用户日志 > 人工编写 > 模型生成（必须人工复核）。
  量不在多，10～50 条高质量题目就足以暴露大问题；但要覆盖每篇文档、各种问法。
- **参考答案不是唯一正确答案**：同一事实有无数种表述，这正是字符串匹配类指标的硬伤，
  也是"关键词命中率"只能当玩具指标的原因。
- **评估要可复现**：结果落盘缓存（模型允许时再把 `temperature` 固定下来），
  两次运行分数才可比较。

## 常见错误

- **拿文档原文当问题**：模型"背过"答案，分数虚高。问题要换成真实用户的口语化问法。
- **一次改多个变量**：换模型同时又改提示词，分数变了无法归因。每次只动一个变量。
- **关键词不做归一化**：大小写、空格、数字写法（18 vs 十八）不处理，命中率全是噪声。
- **评估集只建不养**：产品文档更新后不同步更新评估集，考的还是旧知识。

## 练习建议

1. 给评估集补 3 条"知识库里没有答案"的问题（如"支持 Linux 客户端吗"），
   参考答案写"不知道"，观察模型会不会如实承认。
2. 把关键词命中率换成"参考答案与生成答案的字符 2-gram 重合率"，
   对比两种字面指标在同一份回答上的结论差异。
3. 让 LLM 根据知识库自动出 5 道题，自己人工筛一遍，体会
   "模型出题 + 人工复核"这条评估集生产流水线的效率与坑。
