# 02 LLM-as-Judge：让模型当裁判

第 1 章已经证明：关键词匹配既会冤枉好答案（换个说法就零分），也会放过坏答案
（关键词全中但事实错误）。"判断回答好不好"本身就是语言理解任务——那就让 LLM 来做。
本章用 rubric + judge 提示词给第 1 章生成的回答逐条打分，并用一版故意写差的提示词
验证：评估确实能把好系统和差系统区分开。

## 本章要点

- **评分 rubric 先行**：`correctness`（对照参考答案，事实是否正确完整）与
  `faithfulness`（是否只基于给定资料、有无编造）各打 1-5 分，两个维度独立评，
  混在一起就说不清问题出在哪。
- **judge 提示词三件套**：rubric 定义（含 1/3/5 分锚点）、完整输入材料
  （问题 / 参考资料 / 参考答案 / 待评回答）、严格 JSON 输出格式。
- **结构化解析要兜底**：正则提取输出中的 JSON、分数裁剪到 [1,5]、解析失败给默认值——
  judge 也是 LLM，输出格式不能盲信。
- **评估要先证明能区分好坏**：同一评估集，好提示词（给资料）与差提示词
  （无资料 + 鼓励发挥）各生成一组回答，judge 平均分应明显下降。
  区分不开好坏系统的评估指标，等于没有指标。

## 运行

需要聊天模型密钥（`OPENAI_API_KEY`，第三方服务追加 `OPENAI_BASE_URL` / `MODEL_NAME`）：

```bash
uv run tutorials/evaluation/02_llm_judge/main.py
```

预期输出：好提示词版逐条评分表（正确性 / 忠实度 / 一句话理由）、差提示词版评分表、
两版平均分对比。典型结果是好版两个维度都接近满分，差版忠实度明显塌陷（编造价格、
功能等资料中不存在的信息）。**分数仅为示例**，实际数值因模型和运行而异；
回答与评分都落盘缓存（`answers_cache.json` / `judge_cache.json`），重复运行不再调用 API。

## 核心概念

- **LLM-as-judge 的适用边界**：适合开放式、主观的评估（回答质量、幻觉检测）；
  有确定答案的场景（分类准确率、JSON 能否解析）优先用程序化指标，更便宜也更稳定。
- **judge 的已知偏差**：冗长偏差（偏爱长答案）、自我偏好（同家模型互评偏高）、
  位置偏差（对比评估时偏爱先出现的）。缓解办法：rubric 写具体、控制答案长度、
  换一个不同厂商的模型当 judge 交叉验证。
- **judge 本身也要被评估**：抽一小批人工打分，算与 judge 的一致率；
  一致率低时先改 rubric，而不是怀疑系统。
- **忠实度是 RAG 的命门指标**：答得"对"但资料里没有 = 幻觉。忠实度专门抓这一类，
  这也是评估集里要记录 `source` 的原因——judge 只拿对应文档当依据。

## 常见错误

- **rubric 空泛**："回答质量如何，打 1-5 分" → judge 分数随机漂移。
  每个维度要给清晰的锚点定义，并写明"语义等价即算正确"。
- **把参考答案当唯一答案**：意思对但措辞不同被误判低分——rubric 里必须声明这一点。
- **不做缓存、不控制随机性**：同一评估跑两次分数不同，改动前后无法对比
  （模型允许时可固定 `temperature`，但缓存才是底线）。
- **只看平均分**：5 条满分 + 5 条零分，平均 3 分看起来"还行"。逐条看表才能定位问题。
- **让被测模型自己评自己且不做任何交叉检查**：自我偏好会系统性抬分。

## 练习建议

1. 给 rubric 增加第三个维度"简洁性"（1-5），观察差提示词版在该维度是否同样更差。
2. 换一个不同厂商/系列的模型当 judge 重跑一遍，对比两个 judge 打分的差异，
   体会"自我偏好"问题。
3. 手工给好提示词版的 10 条回答打 1-5 分，计算与 judge 完全一致的比例（一致率），
   想想不一致的条目是 judge 错了还是你错了。
