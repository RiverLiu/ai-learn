# 03 检索质量评估：RAG 的"上半场"打分

RAG 答非所问，多半是**检索就没命中**，而不是模型笨。生成质量需要 LLM judge（第 2 章），
检索质量却有一个干净的程序化指标：该命中的内容，在不在 Top-K 结果里。
本章手写 numpy 余弦检索（与 rag 教程同款），对三种切块配置算命中率——
chunk 大小该选 200 还是 500？让数据回答，不要拍脑袋。

## 本章要点

- **检索评估集很轻**：`question → source`（应命中的文档）+ `gold`（回答问题所需的
  关键原文，即"金句"），不需要完整参考答案，构建成本比 QA 评估集低得多。
- **命中判定分两级**：文档级（Top-K 包含目标文档）宽松；金句级（Top-K 中有块
  包含金句原文）严格。小知识库上文档级会"满分失真"，金句级才有区分度。
- **Hit Rate@K**：金句块进入 Top-K 即命中，按全部问题算命中率；再看金句块的
  **名次**还能算 @1 命中率——@3 全中时，@1 仍能分出高下。
- **检索实现没有任何新东西**：归一化向量 + `vectors @ query` 矩阵乘法 + `argsort`，
  与 rag 教程第 1、3 章一致——本章的重点是"评估"而非"检索"。

## 运行

需要 Embedding 密钥（`OPENAI_API_KEY`，第三方服务追加 `OPENAI_BASE_URL` / `EMBEDDING_MODEL`）：

```bash
uv run tutorials/evaluation/03_rag_metrics/main.py
```

预期输出：三种切块配置的块数、逐问题的金句块名次表（1/2/3/`✗`），最后是命中率对比。
实测输出（使用 qwen3.7-text-embedding，换模型数值会变）：

```
===== 命中率对比（金句级判定） =====
配置            文档级@3       金句级@1       金句级@3
固定窗口200字符   10/10 = 100%  7/10 = 70%    10/10 = 100%
固定窗口500字符   10/10 = 100%  7/10 = 70%    10/10 = 100%
按标题结构切块    10/10 = 100%  10/10 = 100%  10/10 = 100%
```

这张表有三个值得读出的结论：

- **文档级@3 全员满分**：只有 3 篇文档、Top-3 兜底，判定粒度太粗撞上天花板——
  指标没有区分度，等于白评。评估设计的第一课：先看指标能不能区分配置。
- **金句级@1 拉开差距**：按标题切块 10/10，固定窗口只有 7/10。固定窗口把答案句
  切离它所属的标题上下文（"学生凭edu邮箱可申请半价优惠"与"## 专业版"分家），
  块的语义变弱、排名下滑——这正是 rag 教程第 2 章推荐结构感知切块的量化证据。
- **金句级@3 又全满分**：索引只有 6~16 个块时 Top-3 太宽松，参数差异被兜住了。
  真实知识库成千上万块时，@1 的差距会直接影响塞进提示词的内容质量。

## 核心概念

- **检索与生成分开评估**：生成效果差时先查检索（打印 Top-K 看命中），
  检索命中率低的时候去调生成提示词，是无效优化。
- **Hit Rate 之外的常用检索指标**：MRR（目标名次的倒数平均，越靠前越好）、
  Recall@K（问题需要命中多篇时的召回比例）、nDCG（考虑排序位置）。
- **命中率有天花板**：评估问题照抄文档用词、判定粒度太粗、K 相对索引太大，
  都会让指标"满分失真"，区分不出参数好坏——问题要口语化、判定要到金句级。
- **结论只在本评估集上成立**：换知识库、换 Embedding 模型都要重跑重测，
  不要把这里的数字当成普遍真理。

## 常见错误

- **索引和查询走了不同的 Embedding 模型或预处理**：分数全面异常且难以排查。
  索引换模型必须重建，查询侧必须同步。
- **评估问题照抄文档原文**：所有配置全中，得出"切块无所谓"的错误结论。
- **判定粒度过粗**：只数"目标文档在不在 Top-K"，小索引上永远 100%。
- **向量忘记归一化**：拿点积当余弦相似度，长文档会系统性占便宜。

## 练习建议

1. 把 `TOP_K` 改成 1 和 5 各跑一遍，观察三种配置的命中率差距如何放大/消失。
2. 增加一条需要同时命中两篇文档的问题（如"免费版和专业版的历史版本保留有何不同"），
   把判定逻辑从"命中即得分"改成 Recall@K（命中几篇 / 应命中几篇）。
3. 换一个 Embedding 模型重跑本脚本，对比三种切块配置的排名是否变化，
   体会"评估驱动选型"。
