# 03 交接模式：把对话交给下一位

主管模式是"派单—回收"，每轮都由中枢重新决策；客服对话里更常见的是**转接**——
售前发现你要退款，把你转给售后，之后就是售后陪你聊完。控制权一次性转移、
不回头，这就是交接（Handoff）模式。

## 本章要点

- **交接落在 State 的一个字段上**：`current_agent` 被售后节点改写后，
  后续轮次的入口路由直接把对话交给售后——即使闲聊也不再回到售前。
- 两条条件边各司其职：入口条件边按状态选"本轮谁接待"；售前节点后的条件边
  处理"本轮内转接"（检测到退款意图 → 售后节点接管并完成交接）。
- **与主管模式的本质区别**：没有中枢，权力在节点之间转移；
  决策频率从"每轮一次"降为"转移时一次"，更省调用，但也更难收回控制权。

## 运行

```bash
uv run tutorials/multi_agent/03_handoff/main.py
```

预期输出：第 1 轮售前接待（售前口径）；第 2 轮用户提退款，售前转接、售后接管
（口径变为退款政策）；第 3 轮闲聊仍由售后回答——交接已经发生，不再回到售前。

## 核心概念

**三种模式对比**：

| 维度 | 流水线（01） | 主管模式（02） | 交接模式（03） |
| --- | --- | --- | --- |
| 控制流 | 固定直线，无分支 | 中枢每轮决策，星型分发 | 状态驱动，一旦转移不回头 |
| 上下文共享 | State 字段逐站交接 | 本章共享 State；deepagents 版子代理上下文隔离 | 整个 State（含 current_agent）随对话延续 |
| 适用场景 | 步骤固定的批处理（写稿、报告） | 意图分诊、任务调度 | 多轮对话的角色转接（客服、导购） |
| 成本 | 每任务 N 次调用，完全可预期 | 每轮多一次分派调用 | 平时单次调用，只在交接轮多一次 |

**选型决策树**：

```
任务怎么走？
├─ 步骤固定、一路向前 ──────────────────→ 流水线
├─ 每轮都要中枢判断"派给谁"、结果还要 ────→ 主管模式
│   收回中枢继续决策
└─ 对话中角色一次性转移、之后长期 ────────→ 交接模式
    由新角色接管
```

现实中的交接：客服系统"转人工"、ChatGPT 在不同 Agent 模式间切换。
共同点都是**把"当前谁负责"显式建模进状态**，而不是指望模型自己记住。

## 常见错误

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 交接后下一轮又回到售前 | 只改了局部变量，没写回 State | 节点返回 `{"current_agent": ...}` |
| 售前自己处理起退款 | 提示词没禁止越权 | 明确"不要自己处理售后问题" |
| 交接后新角色不知道前情 | 交接只转了控制权，没转上下文 | 把对话关键信息留在 State 里（练习 3） |

## 练习建议

1. 加第 3 个角色"技术支持"，设计售前 → 售后 → 技术的多级交接。
2. 给交接加"反悔"路径：售后判断是误转时，把 `current_agent` 交还售前。
3. 把对话历史放进 State（`messages` 字段，对照
   [langgraph 05 章](../../langgraph/05_persistence/)），让售后接管时能看到售前说过什么。
