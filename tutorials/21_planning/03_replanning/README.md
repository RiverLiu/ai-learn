# 03 动态重规划：计划赶不上变化

现实任务很少一帆风顺：API 失败、资源不可用、用户临时改需求。Replanning 模式让 Agent **在执行过程中监测结果，遇到失败就调整剩余计划**。

## 本章要点

- **失败检测**：执行节点返回的结果里包含“已订满”“失败”等信号，条件边据此进入重规划分支。
- **重规划输入**：已完成步骤 + 失败原因 + 原计划剩余步骤，模型据此生成新的剩余步骤。
- **重规划次数上限**：避免无限循环，设置 `MAX_REPLAN`。
- **适用边界**：外部环境动态变化、工具可能失败、需要容错的长任务。

## 运行

```bash
uv run tutorials/21_planning/03_replanning/main.py
```

任务为“今晚 19:00 预订一家适合 4 人的餐厅”。模型可能会先尝试热门餐厅，遇到“已订满”后自动更换备选方案。

输出会打印：

1. 初始计划。
2. 每一步执行结果，以及是否触发重规划。
3. 重规划次数和最终回答。

## 核心概念

- **条件边里的失败检测**：`route_after_execute` 根据上一步结果决定下一步走哪里。
- **新计划 = 已完成步骤 + 调整后剩余步骤**：保留已经成功的前序步骤，只改后面的路。
- **最大重规划次数**：防止模型在死胡同里无限重试。

## 常见错误

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 重规划后还是走同一条路 | 模型没从失败中学习 | 在 replan prompt 里明确“必须避开已失败选项” |
| 无限重规划 | 缺少 `MAX_REPLAN` | 设置硬上限，超过后直接总结或转人工 |
| 成功结果被误判为失败 | 失败关键词太宽泛 | 用更精确的信号，如返回结构化状态码 |
| 重规划只改措辞不改动作 | 模型没理解工具语义 | 在 prompt 里给出工具调用示例 |

## 练习建议

1. 把失败检测从字符串匹配改成结构化输出：让执行节点返回 `success: bool` 字段。
2. 增加“用户改需求”场景：执行到一半时把目标改掉，观察 Agent 是否会重规划。
3. 把重规划节点接入人工审批：超过一次重规划后暂停，等人确认再继续。
4. 对比本章与 01 章：在任务稳定时，Plan-and-Execute 更简洁；在环境多变时，Replanning 更鲁棒。
