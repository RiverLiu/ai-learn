# 02 文档切块（Chunking）

向量检索的基本单位是"块"而不是整篇文档：文档太长，整体 embedding 会稀释语义，
也塞不进提示词。切块的质量直接决定检索质量——这是 RAG 中最容易被低估的一环。

## 本章要点

- **固定窗口切块**：每 N 字符一刀，相邻块保留重叠（overlap）防止答案正好被切断。
  实现简单，但会粗暴切断句子和小节。
- **结构感知切块**：按 Markdown 标题、段落等天然边界切，每个块语义完整、自带标题上下文；
  个别过长的小节再按段落细分。生产中的默认推荐。
- 每个块都要**记录来源**（`source` 字段），第 4 章靠它给答案附出处。

## 运行

不调用任何 API：

```bash
uv run tutorials/07_rag/02_chunking/main.py
```

预期输出：对比两种策略在示例知识库上的切块结果——固定窗口产生更多碎块且可能拦腰切断句子，
结构切块则与文档的 `##` 小节一一对应。

## 核心概念

- **块大小的权衡**：块太小 → 上下文不全，答案被切碎；块太大 → 噪声多、embedding 语义被稀释、浪费 token。
  中文知识库常见的起点是 200～500 字符，再按实际检索效果调。
- **重叠（overlap）**：固定窗口的补救手段，一般取块大小的 10%～20%。
- **更进一步**：生产系统还会做父子块（小块检索、大块喂给 LLM）、按 token 而非字符计量、
  给每块附加文档标题/摘要等元数据。
