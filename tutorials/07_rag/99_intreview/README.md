# 99 RAG 高频面试题


## 使用方式

- 面试回答先讲结论，再讲链路，最后讲工程权衡。
- 不要背固定数值。性能、成本、召回率提升都和数据集、模型、硬件、索引参数有关。
- 能把问题拆到"数据、检索、排序、生成、评估、上线监控"六层，通常比只讲某个工具更有说服力。

## Q1：什么是 RAG？为什么需要 RAG？

参考答案：RAG 是 Retrieval-Augmented Generation，中文通常叫检索增强生成。核心思想是：回答前先从外部知识库检索相关资料，再让大模型基于检索结果生成答案。

RAG 主要解决四类问题：

| 问题 | 纯 LLM 的风险 | RAG 的价值 |
| --- | --- | --- |
| 知识过时 | 只能依赖训练时已有知识 | 知识库可随时更新 |
| 私有知识 | 不知道企业内部文档 | 可接入内部知识库 |
| 幻觉 | 可能编造事实 | 基于证据回答并可拒答 |
| 可追溯性 | 很难说明答案来源 | 可返回引用和来源 |

高分回答可以补一句：RAG 不能完全消除幻觉，它只是把答案约束到可检索证据上。检索失败、上下文噪声、文档过期或模型不忠实仍会导致错误。

## Q2：RAG 的完整流程是什么？

参考答案：RAG 通常有两条流水线。

离线索引流水线：

```text
文档采集 → 文档解析 → 清洗 → 切块 → embedding → 写入向量库 / 关键词索引 / 元数据库
```

在线查询流水线：

```text
用户问题 → 查询改写 → 检索 → rerank → 上下文组装 → LLM 生成 → 引用 / 拒答 / 日志记录
```

基础版可以只做向量检索 Top-K；生产版通常还会加入权限过滤、混合检索、重排序、上下文压缩、引用校验、质量评估和可观测性。

## Q3：为什么 RAG 要用向量数据库？普通数据库不行吗？

参考答案：向量数据库适合做语义相似度检索，普通关系型数据库更适合结构化查询和精确匹配。

| 类型 | 擅长能力 | 典型用途 |
| --- | --- | --- |
| MySQL / PostgreSQL | 精确查询、事务、结构化过滤 | 用户、订单、权限、元数据 |
| Elasticsearch / OpenSearch | 关键词检索、BM25、过滤聚合 | 关键词召回、日志检索 |
| pgvector | 在 PostgreSQL 中做向量检索 | 中小规模、架构简单 |
| Qdrant / Milvus / Weaviate / Chroma | 向量索引、ANN、相似度搜索 | 大规模语义检索 |

需要纠正的一点：不能简单说向量库一定是 `O(log N)`，也不能说一定比 MySQL 快 100 倍。实际性能取决于数据规模、维度、索引类型、召回率要求、硬件和过滤条件。更准确的说法是：向量库通过 HNSW、IVF、PQ 等近似最近邻索引，在可接受召回率下显著减少全量扫描成本。

## Q4：Embedding 是什么？向量维度是什么意思？

参考答案：Embedding 是把文本映射成稠密向量，让语义相近的文本在向量空间中更接近。向量维度表示模型输出的特征长度，例如 768、1024、1536 或 3072 维。

需要注意：

- 维度不是人工可解释字段，不能把每一维简单理解成"年龄、职业、地域"。
- 同一个知识库的索引和查询必须使用同一个 embedding 模型和同一套预处理方式。
- 换 embedding 模型后，旧向量通常不能复用，需要重建索引。
- 向量相似度常用 cosine、dot product 或 L2，具体选择要和模型训练方式、是否归一化匹配。

面试话术：Embedding 是语义检索的基础，我会关注模型语言能力、领域适配、向量维度、最大输入长度、成本、延迟和是否需要本地部署。

## Q5：设计一个企业级知识库问答系统，你会怎么架构？

参考答案：我会按数据层、检索层、生成层、评估层和运维层设计。

```text
数据源
  ↓
解析清洗：PDF / Word / Markdown / 网页 / 表格
  ↓
切块与 metadata：doc_id、版本、权限、来源、页码、标题
  ↓
索引：向量索引 + BM25 索引 + 元数据库
  ↓
检索：权限过滤 + query rewrite + hybrid search + rerank
  ↓
生成：上下文组装 + 引用约束 + 拒答策略
  ↓
评估与监控：Hit Rate、Recall、MRR、faithfulness、延迟、成本、反馈
```

关键设计点：

- 频繁更新的知识优先用 RAG，不优先用微调。
- 文档解析要保留结构，尤其是标题、表格、页码和版本。
- 企业知识库必须做权限过滤，不能检索到用户无权访问的 chunk。
- 生成答案必须带引用，并在无证据时拒答。
- 上线前用离线评估集，上线后用日志、反馈和抽检持续监控。

## Q6：如何选择 Chunk 大小？有什么影响？

参考答案：Chunk 大小是召回精度和上下文完整性的权衡。

| Chunk 偏小 | Chunk 偏大 |
| --- | --- |
| 检索更精确 | 上下文更完整 |
| 容易丢失前后文 | 容易引入噪声 |
| 适合 FAQ、代码、短条款 | 适合长段解释、政策、报告 |
| 需要父子块或窗口补上下文 | 需要 rerank 或压缩去噪 |

经验起点可以是中文 200-500 字符或英文 300-800 tokens，但不能当成固定答案。正确做法是基于评估集对比不同 chunk size、overlap、结构化切块和父子块策略。

高分回答：我会优先使用结构感知切块，例如按 Markdown 标题、段落、表格边界切分；固定窗口只作为兜底方案。

## Q7：如何解决检索结果不相关或召回质量差？

参考答案：先定位是召回问题、排序问题，还是生成问题。检索不相关通常从以下方向优化：

1. 优化数据：清洗噪声、保留标题、补 metadata、修复表格和 OCR。
2. 优化切块：调整大小、重叠、结构切块、父子块、句子窗口。
3. 优化查询：补全多轮上下文、query rewrite、Multi-Query、HyDE。
4. 混合检索：向量检索 + BM25，通过 RRF 或加权融合。
5. 加 rerank：先召回较多候选，再用 cross-encoder reranker 精排。
6. 换 embedding：选择更适合语言和领域的 embedding 模型。
7. 建评估集：用 Hit Rate@K、Recall@K、MRR、nDCG 对比策略。

不要只靠调 prompt。Top-K 里没有正确证据时，prompt 很难补救。

## Q8：如何降低 RAG 系统成本？

参考答案：RAG 成本主要来自 embedding、rerank、LLM 输入输出 token、缓存存储和日志。优化要保证质量不明显下降。

常用策略：

- 语义缓存：相似问题命中缓存，但要处理知识库版本、权限和过期。
- 控制 Top-K：召回阶段可以多，最终进入 LLM 的上下文要少而准。
- rerank 后再截断：减少无关 chunk 占用 prompt。
- 上下文压缩：只保留与问题相关的句子或段落。
- 模型路由：简单问题用小模型，复杂问题用强模型。
- 批处理 embedding：离线索引时批量向量化。
- 增量更新：文档变化时只重建相关 chunk。

需要纠正：不要承诺语义缓存一定有 30%-50% 命中率，或上下文压缩一定减少 40% token。实际收益要用线上流量分布和评估集验证。

## Q9：什么是语义缓存？如何实现？

参考答案：语义缓存不是要求用户问题完全相同，而是用 embedding 判断两个问题语义是否足够接近。如果命中缓存，可以直接返回已有答案，降低延迟和成本。

核心流程：

```text
用户问题 → query embedding → 检索缓存向量 → 相似度超过阈值？
  是 → 校验租户、权限、知识库版本、TTL → 返回缓存答案
  否 → 走正常 RAG → 写入缓存
```

关键问题：

- 相似度阈值太高会漏命中，太低会返回错误答案。
- 多租户和权限场景必须隔离缓存。
- 知识库更新后，缓存要按版本失效。
- 对时效性问题、个性化问题、强权限问题要谨慎缓存。
- 缓存命中也要记录日志，便于后续排查。

高分回答：语义缓存是成本优化手段，不是质量优化手段。上线前要用回放流量验证误命中率。

## Q10：什么是 Query 改写？如何提升检索效果？

参考答案：Query 改写是把用户原始问题改成更适合检索的查询。用户问题经常省略主语、依赖历史上下文、口语化或过短，直接 embedding 可能召回不到正确文档。

常见策略：

| 策略 | 作用 | 示例 |
| --- | --- | --- |
| 多轮补全 | 把省略问题改成独立问题 | "它怎么实现？" → "RAG 系统怎么实现？" |
| 查询扩展 | 增加同义表达 | "报销" → "费用报销、发票、审批流程" |
| Multi-Query | 生成多个查询分别检索 | 从不同角度召回 |
| HyDE | 先生成假设答案再检索 | 用更像文档的文本做检索 |
| 意图分类 | 选择不同检索器 | FAQ、政策、代码、表格走不同策略 |

注意：Query 改写可能引入错误意图，所以需要保留原问题，并记录 rewritten query 用于调试。重要场景可以同时检索原问题和改写问题，再合并结果。

## Q11：什么是上下文压缩？如何减少无效 token？

参考答案：上下文压缩是在检索后、生成前，从候选文档中保留最相关的信息，减少无关 token 对成本、延迟和答案质量的影响。

常见方法：

- Rerank 后只取 Top-N。
- 按句子或段落过滤，只保留与 query 相似度高的片段。
- 用 LLM 提取与问题相关的句子。
- 对长文档使用摘要或结构化提纲。
- 使用父子块：小块检索，大块或窗口生成。

需要区分：上下文压缩不是越短越好。压缩过度会丢失限制条件、例外条款和必要背景。应该用 completeness、faithfulness、answer correctness 和 token cost 一起评估。

## Q12：Late Chunking 是什么？它和普通切块有什么区别？

参考答案：Late Chunking 是一种让 chunk embedding 保留更长上下文信息的技术路线。普通做法通常是先把文档切块，再分别对每个 chunk embedding；Late Chunking 则先让长文本整体经过支持长上下文的 embedding 模型，得到 token-level 表示，再按 chunk 边界池化出每个 chunk 的向量。

需要纠正：Late Chunking 不是简单地"先得到一个整篇文档向量，再把这个向量切开"。向量本身没有可直接切分的文本边界。关键在于利用模型对长上下文的 token 表示，再为每个 chunk 聚合向量。

适用场景：

- 文档上下文强，单独 chunk 容易语义不完整。
- 模型支持足够长的输入。
- 可以接受更高的索引构建成本。

## Q13：Embedding 模型如何选择？

参考答案：选择 embedding 模型要看语言、领域、效果、成本、延迟、部署方式和最大输入长度。

| 维度 | 关注点 |
| --- | --- |
| 语言 | 中文、英文、多语言、跨语言 |
| 领域 | 通用、代码、法律、医疗、金融 |
| 指标 | MTEB、C-MTEB、领域评估集上的 Recall / nDCG |
| 成本 | API 单价、本地 GPU 成本、批处理能力 |
| 延迟 | 单条和批量 embedding 延迟 |
| 维度 | 存储成本、检索速度、精度 |
| 部署 | 云 API、本地模型、私有化要求 |

面试中可以这样回答：我不会只看排行榜，会在自己的 RAG 评估集上对比模型。中文或中英混合可以评估 BGE 系列、多语言模型或商业 embedding；数据敏感时倾向本地部署；如果使用 API，需要考虑数据合规和成本。

## Q14：GraphRAG 是什么？与普通向量 RAG 有什么区别？

参考答案：GraphRAG 是把知识图谱和 RAG 结合起来，用实体、关系和图遍历增强检索与推理。它适合关系密集、多跳推理和强解释性的场景。

| 维度 | 向量 RAG | GraphRAG |
| --- | --- | --- |
| 数据组织 | 文本 chunk + embedding | 实体、关系、社区、路径 |
| 检索方式 | 语义相似度 | 图查询、图遍历、图摘要，可结合向量检索 |
| 优势 | 构建快、适合文档问答 | 多跳关系、可解释性更好 |
| 难点 | 多跳推理弱 | 图谱构建、关系抽取、维护成本高 |

需要注意：GraphRAG 不是向量 RAG 的通用替代。自由文本问答、FAQ、客服知识库通常先用向量 RAG 或混合检索；当问题核心是实体关系、跨文档关联、社区摘要和多跳推理时，再考虑 GraphRAG。

工程安全点：如果让 LLM 生成 Cypher 或 SQL，必须做只读限制、语法校验、超时、白名单和权限控制，不能直接执行任意查询。

## Q15：Agentic RAG 是什么？与普通 RAG 的区别是什么？

参考答案：普通 RAG 通常按固定流程检索一次并生成答案；Agentic RAG 让 Agent 根据问题和已有上下文动态决定是否检索、检索什么、是否拆解子问题、是否继续检索以及何时回答。

典型流程：

```text
用户问题
  ↓
Agent 判断问题类型
  ↓
选择工具：向量检索 / 关键词检索 / Web / 数据库 / 图查询
  ↓
评估证据是否充分
  ↓
不充分则继续检索或拆解子问题
  ↓
生成带引用的答案
```

优势：

- 适合复杂、多跳、开放域问题。
- 能按需调用不同检索工具。
- 可以在证据不足时继续查找或拒答。

风险：

- 成本和延迟更高。
- 工具调用可能失控，需要最大轮数和预算限制。
- 更难评估和复现，需要完整 trace。
- 需要防 prompt injection 和工具滥用。

## Q16：Parent-Document Retrieval 和 Sentence Window Retrieval 是什么？

参考答案：这两种方法都在解决"小块检索精准，但上下文不完整；大块上下文完整，但检索不精准"的矛盾。

Parent-Document Retrieval：

```text
父块：较大的段落或小节，用于最终给 LLM
子块：较小的 chunk，用于 embedding 和检索
检索命中子块后，返回对应父块
```

Sentence Window Retrieval：

```text
按句子建索引
检索命中某一句
生成时返回该句前后 N 句作为窗口上下文
```

对比：

| 方法 | 检索粒度 | 返回粒度 | 适用场景 |
| --- | --- | --- | --- |
| Parent-Document | 小 chunk | 父段落 / 父小节 | 长文档、层级结构明显 |
| Sentence Window | 单句 | 前后句窗口 | 精确问答、政策条款、技术说明 |

## Q17：如何做 RAG 知识库的动态更新？

参考答案：知识库更新的核心是让索引、metadata、缓存和线上查询保持一致。

常见策略：

- 全量重建：简单可靠，适合低频更新；可用蓝绿索引降低停机风险。
- 增量更新：只处理新增、修改、删除文档；需要稳定的 `doc_id` 和 `chunk_id`。
- 实时更新：通过消息队列或 CDC 监听文档变更，适合高实时性场景。
- 版本化索引：每次发布一个新版本，支持灰度、回滚和 A/B 测试。

关键细节：

- 文档修改后，旧 chunk 和旧 embedding 要删除或失效。
- metadata 要保存文档版本、更新时间和来源。
- 语义缓存要跟随知识库版本失效。
- 切换新索引前要跑评估集，避免新数据管道破坏检索质量。
- 删除文档要考虑权限和合规，不能只从元数据库删而保留向量。

## Q18：什么是多模态 RAG？如何实现图文混合检索？

参考答案：多模态 RAG 是知识库同时包含文本、图片、图表、扫描 PDF、音频或视频等内容，系统能检索并利用多种模态的信息回答问题。

常见方案：

| 方案 | 思路 | 优点 | 局限 |
| --- | --- | --- | --- |
| OCR / Caption → 文本 RAG | 把图片、表格、PDF 页面转成文字描述后入库 | 实现简单，兼容现有 RAG | 依赖 OCR 和 caption 质量 |
| 多模态 embedding | 图文映射到统一向量空间 | 支持图文互搜 | 领域效果需要评估 |
| 页面级视觉检索 | 把 PDF 页面作为图片检索，例如 ColPali 类方案 | 对复杂版面和图表更友好 | 部署成本高 |
| 混合方案 | 文本、图片描述、页面向量一起召回 | 覆盖面更好 | 系统复杂度更高 |

面试回答时要补充：图表和表格不能只做普通 OCR，还要保留行列关系、标题、页码和图片位置，否则答案可追溯性会很差。

## Q19：如何处理复杂 PDF 表格？

参考答案：复杂 PDF 表格的难点是版面结构、跨页表格、合并单元格、扫描件 OCR 和行列关系。不能只把 PDF 当纯文本抽取。

推荐流程：

1. 判断 PDF 类型：可复制文本、扫描件、混合型。
2. 做版面分析：识别标题、正文、表格、图片、页眉页脚。
3. 表格单独抽取：保留行列、表头、单位、脚注和跨页关系。
4. 转成 Markdown 表格或结构化 JSON。
5. 为表格 chunk 添加 metadata：页码、表名、列名、来源。
6. 对关键表格做人工抽检或规则校验。
7. 对图表类内容补充 caption 或使用多模态检索。

需要谨慎回答准确率提升数字。可以说"在某项目中通过版面分析和表格结构化显著提升准确率"，不要把具体 65% 到 94% 当成通用结论。

## Q20：如何建立 RAG 系统的生产级可观测性？

参考答案：RAG 可观测性要分层记录，而不是只看 API 成功率和延迟。

需要记录：

- 输入：用户问题、会话、租户、权限范围。
- 查询处理：改写后的 query、意图、检索策略。
- 检索结果：Top-K chunk、分数、doc_id、版本、metadata、rerank 分数。
- 生成过程：最终 prompt、模型、temperature、token、延迟。
- 输出：答案、引用、拒答原因、置信度。
- 反馈：点赞点踩、追问、转人工、人工标注。

关键指标：

| 层级 | 指标 |
| --- | --- |
| 检索质量 | Hit Rate@K、Recall@K、MRR、nDCG、无结果率 |
| 生成质量 | Faithfulness、Answer Relevance、Correctness、Completeness |
| 引用质量 | Citation Precision、Citation Recall、Unsupported Claim Rate |
| 系统性能 | p50 / p95 / p99 延迟、TTFT、tokens/sec、错误率 |
| 成本业务 | 单问成本、缓存命中率、点踩率、追问率、转人工率 |

高分回答：上线前用评估集做回归测试，上线后用 trace 定位单次失败样本，并定期抽样人工评审。可观测性的价值是把"答案不好"定位到检索、排序、生成、引用或数据更新中的具体一层。

## Q21：RAG 效果不好如何排查和提升？

参考答案：按链路从前往后排查。

```text
答案不好
  ↓
Top-K 是否包含正确证据？
  否：查数据清洗、chunk、embedding、query rewrite、hybrid search
  是
  ↓
正确证据排名是否靠前？
  否：加 rerank、调融合策略、调 Top-K
  是
  ↓
上下文是否太长或噪声太多？
  是：上下文压缩、父子块、去重、过滤
  否
  ↓
模型是否忠实回答？
  否：改 prompt、降低温度、加引用约束、做 faithfulness 校验
  是
  ↓
看评估集覆盖和线上真实问法
```

不要只讲"换更好的模型"。成熟回答应该能说明具体指标，例如检索看 Recall@K / MRR，生成看 Faithfulness / Correctness，线上看负反馈率和追问率。

## Q22：RAG 出现幻觉怎么办？

参考答案：先判断幻觉来源，再分层处理。

| 类型 | 可能原因 | 处理方式 |
| --- | --- | --- |
| 检索幻觉 | 检索内容不相关 | 提升召回、rerank、拒答阈值 |
| 融合幻觉 | 多个 chunk 冲突 | 引入版本、时间、来源优先级 |
| 过度推断 | 模型补充上下文外信息 | 强化 prompt 和引用约束 |
| 记忆覆盖 | 模型用训练知识覆盖资料 | 要求以 context 为准，低温生成 |
| 无答案硬答 | 知识库没有答案 | 明确拒答策略 |

防护措施：

- Prompt 明确要求只基于 context 回答。
- 每个关键结论必须有引用。
- 无证据时回答无法根据现有资料确定。
- 对答案做 faithfulness 或 unsupported claims 检查。
- 低置信度转人工或提示用户核实。
- 建立拒答样本评估集，避免模型为了"有帮助"而编造。

合理目标不是"幻觉率为 0"，而是在业务可接受范围内降低幻觉，并让高风险答案可追溯、可拦截。

## 速记卡片

| 概念 | 一句话解释 |
| --- | --- |
| RAG | 先检索证据，再基于证据生成 |
| Embedding | 文本的语义向量表示 |
| Chunking | 把长文档切成可检索、可引用的块 |
| Metadata | 支持引用、权限、版本和排查的结构化信息 |
| Hybrid Search | 向量检索和关键词检索结合 |
| Rerank | 对候选结果做更精细排序 |
| Query Rewrite | 把用户问题改写成更适合检索的查询 |
| HyDE | 生成假设答案，再用假设答案检索 |
| Parent-Document | 小块检索，父块生成 |
| Sentence Window | 单句检索，返回前后句窗口 |
| GraphRAG | 用实体关系图增强多跳检索和推理 |
| Agentic RAG | Agent 动态决定检索策略和轮次 |
| Semantic Cache | 语义相似问题复用答案 |
| Faithfulness | 答案是否被上下文支持 |
| MRR | 正确结果越靠前，分数越高 |
