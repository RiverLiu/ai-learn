# 03 子代理：上下文隔离的分工协作

复杂任务拆给多个子代理，好处不是"人多力量大"，而是**上下文隔离**：
调研员查资料产生的几十条中间消息，只存在于它自己的上下文里，
主代理收到的只有最终结论——主上下文保持干净，才能掌控全局。

## 本章要点

- 子代理用 dict 声明：`name` / `description`（**主代理靠它决定何时派单**，要写好）/
  `system_prompt` / `tools`（可选，不给则用主代理的工具）/ `model`（可选，可给子代理配不同模型）。
- 主代理通过内建的 **`task` 工具**发起调用，参数含 `subagent_type` 和 `description`（任务书）。
- 分工设计：本章主代理**故意不拿查询工具**，逼它只能派 `researcher` 调研；
  报告由主代理亲自写盘，再派 `critic` 审校——职责边界清晰，结果可预期。
- 框架还内置一个名为 `general-purpose` 的默认子代理（继承主代理全部工具），
  不声明 `subagents` 时主代理也能派通用子任务。

## 运行

```bash
uv run tutorials/deepagents/03_subagents/main.py
```

预期输出：`[派单] -> researcher：...` → `[决策] write_file` → `[派单] -> critic：...`
→ 修订 → `[回答] ...`。

## 核心概念

- **子代理 = 一次隔离的 Agent 运行**：它有独立的消息历史，跑完把最后一条消息
  作为工具结果返回给主代理。与[第 2 章](../02_builtin_capabilities/)的文件卸载搭配，
  子代理也常把详细产出写进文件、只回摘要，主代理需要细节时再读文件。
- **派单不是银弹**：每个子代理都是一次完整的模型循环，成本与延迟都翻倍。
  经验法则：子任务会产生大量中间上下文（检索、长阅读）时才值得派。
